Shared MCP: one server per machine, shared by every Claude Code session

The argument, the artifacts, how to operate them, and live evidence — in one page. How Claude Code's per-session MCP servers became shared, supervised, self-registering services; the crash that started it; the kit that makes sharing a plugin's default while staying safe on any machine; the console that keeps the daemons visible; and what remains open.

0How to read this

Front matter

This is the single room for the shared-MCP work: the argument (§1–4: why one server per machine, seen from every concern), the artifacts (§5–9: each file and how it works inside), operating it (§10–12: machine state, undo, edge cases, day to day), and live evidence (§13). Everything marked derived was read from this machine when the page was generated (2026-09-23 03:35 MST); the page regenerates on every commit to the kit and daily at 03:35, so it cannot describe a machine that no longer exists.

The argument half combines the concerns raised while building this — distributed, user, experience, technical, infrastructural, functional, feature, exceptional, ecosystem, development, networking — into one account rather than eleven. The artifact half is the inventory that account rests on.

Nouns used throughout. An MCP server is a program that exposes tools to Claude over the Model Context Protocol. stdio means Claude talks to it through the process's own input and output pipes, which is one-to-one. A gateway is the process that runs one original server and serves it to many clients over HTTP on the loopback interface. A bridge is the small per-session program that speaks stdio to Claude and HTTP to a gateway. launchd is macOS's service manager. svc is the console built for this that lists and manages everything launchd runs for you; a descriptor is the small JSON file that tells svc what launchd cannot know about a service.

1The one sentence

The invariant everything else is a view of

An MCP server is a service that should exist once per machine; a Claude session is a client of it; the plugin that ships the server guarantees that arrangement on any machine, degrading to today's behaviour when it cannot; and the machine's owner sees and manages every such service from one console.

2What a session sees

User · experience · functional · feature · exceptional

User and experience

Nothing changes inside a conversation. Tool names are identical because server names are identical; /mcp lists the same servers; a fresh install's first session works with no setup. The visible differences are negative space: no crash dialog on quit, and gigabytes of memory returned to the machine.

Functional

Every tool, prompt and resource request is forwarded verbatim through the gateway to the single original process. A server that owns state — a database file, a lock — now has exactly one owner, so two sessions writing at once no longer fight.

Feature

Sharing is the plugin's default, not a per-machine override. The entire feature surface a plugin author touches is one line in .mcp.json pointing at the vendored launcher, with the original command after a -- and the environment variables to forward declared with --env.

Exceptional

Failure has a defined shape at every layer, and the ladder ends on the old behaviour, never on a broken server.

3What the machine runs

Infrastructural · technical · networking · distributed

Infrastructural

Each shared server is a launchd agent with a stable label, a state directory under ~/.local/state/shared-mcp/<name>/, a log truncated at 5 MB, and a health endpoint that returns its identity. svc derives its inventory from launchd, the process table and the filesystem on every run, so the list cannot rot; the only authored facts are the ones launchd cannot know — purpose, source, health probe — kept as one small descriptor per service, written by the daemon itself when it starts.

Technical

Three moving parts. The bridge: standard-library Python, about 25 MB, one thread per client message, reconnects and replays when the gateway's session disappears, waits for the initialize handshake before forwarding pipelined messages. The gateway: the mcp library in a private virtualenv, runs the original command once, serves streamable HTTP, pings the child every 15 s and treats an error reply as alive (some servers reject ping) and only silence as dead. The supervisor: launchd here with ProcessType Interactive — without it the agent runs on efficiency cores and a 9 s cold start becomes 50 s, past Claude's 30 s connect timeout — systemd on Linux, a detached process elsewhere.

Networking

Loopback only, never bound off the machine. One port per server, hashed from the server name, so it is stable across restarts and machines and cannot collide between plugins from different authors. That is also why the numbers look arbitrary; legibility is the open question in §6. The spec-vault daemon moved off 8765 because an unidentified local client hammers that port with WebSocket upgrades.

Distributed

Many sessions, one process, per machine; nothing crosses machines. Secrets a server needs are captured once, from the declaring session, into a private spec.json rather than into launchd's plist. A session that cannot even resolve the server's executable keeps a healthy gateway started by a better-equipped session instead of replacing it with a definition that cannot run.

4How it spreads and evolves

Ecosystem · development

Ecosystem

The plugins stay publishable. Anyone installing them from your marketplaces gets the shared behaviour where their machine allows it and the old behaviour where it does not, with no dependency on anything that exists only on this Mac. Claude Code offers no per-user override of a plugin's server definition and no way to disable one plugin server while keeping its skills; redefining a server under your own name changes every tool name and breaks the plugin's skills and agents. The bridge is therefore the only shape that keeps tool names intact for everyone, and the four plugin servers keep bridges by necessity.

Standards (checked 2026-09-15)

MCP specifies stdio as one subprocess per client and Streamable HTTP for many clients; a shared local server is not specified. Converting the former into the latter on loopback is common community practice (mcp-proxy, supergateway, Docker's MCP Gateway) but a plugin installing a login-time service to get there is unusual, so every plugin now discloses it in its README and the launcher prints a first-run notice with the opt-out. Spec release 2026-07-28 (SEP-2575, SEP-2567) removed the initialize handshake, protocol sessions and ping; the bridge is correct in both generations (it waits for or replays initialize only if the client sent one, tracks a session id only if the server issued one, forwards JSON-RPC errors carried on 4xx) and the gateway's liveness probe is an ordinary RPC. Each gateway serves a Server Card (SEP-2127, in review) at /.well-known/mcp/server-cards.json. The roadmap's Transports WG item "HTTP over stdio" would reduce the bridge to a byte relay; the kit's public shape is meant to survive that unchanged, and this machine's case — a dozen clients, single-writer state — is a use case worth bringing to that working group.

Versions

When a server gets a new version: a marketplace install lands in a new folder, so the command path changes and the next session's connect restarts the gateway. A directory-source marketplace or a hand-edited server keeps the same path, so the kit also fingerprints the plugin's declared version and the entry script and restarts on any change; spec-vault's script tracks its version the same way. Running sessions' bridges reconnect and see the new server. Until the next session starts, the old code keeps serving — the same window the old per-session model had between sessions.

Development

One canonical kit, ~/Developer/shared-mcp/shared_mcp.py, with an end-to-end test whose fixture server carries a counter — two sessions seeing 1, 2, 3 is the proof of sharing — and a vendor script that stamps byte-identical copies into plugin roots. Fixes flow outward by re-vendoring and bumping. Three real bugs were found only by running it under your actual load and are now pinned: a restart loop from a rejected health ping, a PATH race between sessions with different environments, and an HTTP redirect on a mounted path. The graph server's own crash was fixed at its source first.

6The crash fix

spec-vault graph-server/server.py — the root cause everything else grew from

Symptom. macOS "Python quit unexpectedly" on every Claude quit. Cause. The graph server's SIGTERM handler called sys.exit(0). That starts Python's interpreter finalization while the MCP library's stdin reader is blocked in a read on a non-daemon worker thread that holds the stdin buffer lock. Finalization waited on that thread forever (servers lingered for days after pid-file takeover), and when Claude closed the pipe the thread woke into a finalizing Python 3.13 interpreter, was parked, and the main thread aborted with "could not acquire lock for <_io.BufferedReader name='<stdin>'> at interpreter shutdown".

Fix (commit f4ee628). The handler now runs the two cleanups itself, guarded against re-entry, and leaves via os._exit(0), skipping finalization and the join. Signal registration moved below the pid-file helpers so the handler can never reference an undefined name. Verified with SIGTERM while stdin open (previously hung forever), stdin EOF then SIGTERM, and double SIGTERM: all exit 0 in under a second.

Then the same file gained --transport http (streamable HTTP via FastMCP, host/port flags or env) so one instance can serve every session — the first shared daemon, before the generic kit existed.

7spec-vault's own daemon

graph-server/daemon.sh + proxy.py — bespoke, predates the kit

daemon.sh is a bash manager the plugin ships. connect (what .mcp.json runs) builds a persistent venv at ~/.local/state/spec-vault/venv when requirements.txt changes, starts the daemon via a generated launchd agent com.spec-vault.graph-server (ProcessType Interactive — without it launchd puts the process on efficiency cores and cold start goes from 9 s to 50 s, past Claude's 30 s connect timeout), restarts it when the plugin path changed after an upgrade, rotates its log at 5 MB, writes an svc descriptor, waits for the port, then execs proxy.py. Other verbs: status, logs, stop (waits for the port to go quiet; removes the descriptor), ensure. It survives two launchd races: bootstrap right after bootout (EIO; retried) and a dying process mistaken for a foreign one.

proxy.py is the per-session bridge, built on the mcp library (~38 MB per session). Its upstream connection lives in one supervising task that reconnects and replays the in-flight call when the daemon restarts; a watchdog polls the daemon's health while a request waits so a call in flight during a restart cannot hang. Port 47765 (moved off 8765, which an unidentified local client hammers with WebSocket upgrades).

Why it still exists alongside the kit. It works, it is the plugin's own code, and the graph server has native HTTP so it needs no gateway wrapper. Migrating it to the kit would trade a heavier bridge for uniformity; recorded as optional.

8The shared-mcp kit

shared_mcp.py — one file that makes sharing a plugin's default while staying safe anywhere

A plugin points its MCP entry at python3 shared_mcp.py connect --name X [--env KEY]... -- <original command>. The file is ~700 lines in six parts, in file order:

spec / pathsbuild_spec resolves the executable with the session's PATH (a venv once shadowed python3), hashes a stable port from the name (47800–48799), captures only the declared env vars, records cwd and the launcher path. ~/.local/state/shared-mcp/<name>/spec.json, mode 0600.
health/health returns an identity card; gateway_ok checks the name so a foreign process on the port is never mistaken for ours.
venvOne shared environment with the mcp package, built by uv if present else python -m venv, rebuilt only when the requirement string changes.
supervisionlaunchd plist (Interactive, KeepAlive, session PATH, venv not prepended) on macOS; systemd --user unit on Linux; detached process + pid file elsewhere. stop_gateway waits for the port to go quiet and removes the descriptor.
ensureHealthy and same definition and same content fingerprint (plugin version + entry-script hash + launcher hash — so an in-place update restarts the gateway even when the path is unchanged) → return. Healthy but this session cannot resolve the executable → keep it. Stale definition → restart. Otherwise build, start, write descriptor, wait up to 60 s, and on the very first run print a disclosure of what is being installed and how to opt out.
BridgeStandard library only (~25 MB). One thread per client message; POSTs to /mcp; parses JSON or SSE replies; forwards JSON-RPC errors carried on 4xx. Waits for the initialize round-trip only if the client sent one; tracks a session id only if the server issued one — correct under both the 2025 protocol and the 2026-07-28 release. On connection loss: wait for the gateway, run ensure after 10 s of silence, re-initialize with the client's own parameters, replay.
gatewayRuns in the venv. stdio_client starts the original command once; a low-level Server forwards tools, prompts and resources; a StreamableHTTPSessionManager behind uvicorn on loopback serves /mcp, /health and a Server Card at /.well-known/mcp/server-cards.json. A watchdog calls tools/list every 30 s; any reply means alive; silence restarts the child. The outer loop restarts the child on any failure.
CLIconnect, ensure|status|stop|logs --name X, gateway --spec (internal). SHARED_MCP_DISABLE=1 runs the original per session.

The test (tests/test_shared.py) is the proof, not the description: two bridges call a fixture server's counter tool and see 1, 2, 3 from one process id with a declared secret forwarded; the gateway is killed and both bridges recover; stdin EOF exits 0; the descriptor is written and removed; and with the state directory made unwritable the original server runs directly. §8 has today's run.

Distribution. vendor.sh copies the file byte-identically into plugin roots. Vendored today into ado-backlog-sync, prompt-library and advanced-prompting-engine; your three personal servers (projam, graphology, efforts) use the canonical copy via ~/.claude.json. 9The svc console

svc.py — one place for everything launchd runs for you

svc is on your PATH (symlink from ~/.local/bin/svc to ~/.local/share/svc/svc.py). Its substrate is derived on every run: it reads the plists in ~/Library/LaunchAgents, asks launchctl print for state, pid and last exit, asks lsof for listening ports, stats the log files, and joins the descriptors in ~/.config/svc/services.d/. Nothing that can be computed is ever written down, so it cannot go stale; a descriptor holds only purpose, source, health probe, friendly name and manage overrides.

svc list [--all]owned services and jobs (vendor and brew agents hidden unless --all)
svc show <name>everything known, including the exact restart/stop/start/logs commands
svc logs <name> [-n N] [-f]tail the real log files
svc healthprobe every owned service; never says ok without evidence
svc doctordormant plists, failing runs, missing programs, both streams discarded, runaway logs, piles of per-run logs, unregistered agents, orphaned descriptors, port clashes
svc start|stop|restart <name> [--go]dry-run without --go; after --go it re-reads reality and refuses to claim success it cannot see
svc prune [--go] [--days N] [--install]truncate live logs over 20 MB to their last 2000 lines; delete rotated/per-run logs older than 14 days; --install registers the daily 03:30 agent com.joshua.svc-prune
svc register <label> [--go]write a descriptor prefilled from derived facts; you fill in purpose
svc selftestfixture tests for plist classification and the launchctl output parser (the one place launchctl's text is read)
svc <anything>dispatches to libexec/svc-<anything> or svc-<anything> on PATH — the extension seam

Health rules worth knowing: a service with KeepAlive only-on-failure that exited 0 is ok, stopped by design; a probe URL's expected status codes are declared in the descriptor; periodic jobs are judged by last exit code. MANIFESTO.md in the repo keeps the honest ledger of what the tool does and does not model.

Fixed after an independent code review (0.3.0)

A high-effort review of the kit returned 23 confirmed findings; all were fixed in 0.3.0 and the two worst are worth knowing: a bridge cached its gateway's port at start, so after a port move it would have posted to a dead port for the rest of the session (now read live); and a reconnect could raise out of the request thread, hanging Claude's tool call instead of returning an error (now never raises, and a failed handshake releases any pipelined messages). Also: the cold-start lock now heartbeats, claims stale locks atomically and never removes another holder's lock; the venv build takes a machine-wide lock; a reconnecting bridge can revive or adopt a gateway but never replace a live one, so an old session cannot downgrade an upgrade; a registered-but-not-yet-answering gateway is waited for instead of torn down; identity is the declared command, not one session's PATH resolution; the watchdog stays quiet while the child is busy and needs two consecutive silences; binary resources are forwarded as bytes; plist and unit strings are escaped. Unit tests in tests/test_unit.py pin the failure paths. A second review pass (0.3.1) found eleven more: resource reads through the gateway failed on a wrong import (now covered by an end-to-end resources/read test); a mid-call network failure could replay a side-effecting tool call (now: replay only when the request provably never dispatched, or the method is idempotent; otherwise the client gets an explicit error); a deadlocked child could hide from the watchdog behind an in-flight counter (now probed anyway after 10 minutes without a completion); a reconnecting bridge could revive a gateway with its own stale definition (now revives with the newest on disk); stale pid files could kill an unrelated process (now the pid must belong to a gateway); --serialize/--cwd changes were ignored; --cwd was dropped on fallback; a failed bootstrap during a graceful shutdown now adopts the surviving gateway instead of spawning a private copy; a port-bind failure no longer loops behind a healthy-looking pid; held locks are released at interpreter exit; a missing --name derives a unique one.

Known limits

  • Server-initiated requests — roots, sampling, elicitation — are not forwarded to a particular session. A server that needs them is per-session by nature; use --per-session. (All three are deprecated in the 2026-07-28 spec.)
  • Server→client notifications (progress, tools-list-changed) are not relayed; a session sees a changed tool list on reconnect.
  • A single tool call longer than 600 s trips the bridge's HTTP timeout.
  • When Claude Code moves to the 2026-07-28 protocol, the gateway's mcp dependency must be bumped; the bridge already tolerates both generations.
  • The systemd --user path is implemented but not exercised here (no Linux host or container runtime). The detached-process path that Windows and systemd-less Linux use is exercised, by forcing the kit off launchd in tests/test_detached.py: start, health, no-op ensure, revive after kill, stop. Its one real limit stands: without a service manager nothing restarts a killed gateway until the next session connects.

12Operating it day to day

The five gestures

  1. Something MCP-ish feels off: svc doctor, then svc show mcp-<name>, then svc logs mcp-<name>.
  2. A tool says the server failed to connect: svc health. If the gateway is up, /mcp reconnect in that session; if not, svc restart mcp-<name> --go (or wait — a bridge revives its gateway after 10 s).
  3. You changed a server's env or command: the next session's connect detects the new definition and restarts the gateway. To force it now: shared_mcp.py stop --name X then start a session.
  4. New plugin with an MCP server: vendor.sh <plugin-dir>, point its .mcp.json at connect, declare forwarded env with --env, add the README disclosure paragraph. Do not share a server that depends on the session's working directory or attaches to a per-session resource.
  5. New background job of any kind: svc register <label> --go and fill in purpose; give it a health probe.

14Open questions and the next step

What is not settled

Legibility of addresses. Hashed ports are correct for plugins shipped to strangers and unmemorable for the owner. For your three personal servers — projam, graphology, efforts — the right answer is one front door: a single process on one readable port with a path per server, e.g. http://127.0.0.1:47800/servers/projam/mcp. The open-source mcp-proxy does exactly this in its server mode, one child per named server shared by every client. It cannot replace the kit inside plugins (it is a package with dependencies, not a single vendorable file, and it has no fallback), but for the personal three it removes 36 bridges and three launchd agents in exchange for one.

Published. The kit is public at github.com/JoshuaRamirez/shared-mcp; the marketplace (Azure DevOps, spec-vault 0.12.0 and ado-backlog-sync 0.4.0), advanced-prompting-engine (feature branch) and claude-code-profile (prompt-library) are pushed.

What direct HTTP gives up. Claude Code reconnects to HTTP servers with backoff, but the documentation does not say whether a terminated session after a gateway restart is retried; a /mcp reconnect may be needed in open sessions after the rare gateway restart. The bridge hides this today.
